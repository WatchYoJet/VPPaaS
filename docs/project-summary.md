# VPPaaS Project — Complete Summary

## What Is This Project?

VPPaaS (Virtual Power Plant as a Service) is the 2026 Enterprise Integration (EI) course project at Instituto Superior Técnico (IST), Universidade de Lisboa. The goal is to build a cloud-based information system that aggregates distributed energy resources (solar panels, batteries, EV chargers) owned by "Prosumers" (producer-consumers) into a unified Virtual Power Plant, enabling grid optimization and energy trading.

The project is delivered in **two sprints**:
- **Sprint 1** (deadline: 10/5/2026): microservices, Kafka cluster, RDS, Terraform deployment, testing
- **Sprint 2** (deadline: 7/6/2026): Camunda BPMN processes, Kong API Gateway, end-to-end integration

## System Architecture

### Domain Concepts

| Concept | Description |
|---|---|
| **Prosumer** | Household/business that consumes AND generates/stores energy (solar, battery, EV) |
| **Utility Operator** | Energy manager of a specific Grid Cell; establishes asset links with prosumers |
| **Grid Cell** | Geographic/logical cluster (e.g., "Lisbon-Downtown"); has capacity constraints |
| **Asset Link** | Digital contract associating a Prosumer's hardware with a Utility Operator |
| **Telemetry** | Real-time data packets (SoC, voltage, current, status) sent by assets |
| **Flexibility Event** | Command/offer generated by VPPaaS (e.g., discharge incentive during grid stress) |
| **Grid Balancing** | Recommendation to shift load between zones when one has deficit and another surplus |

### The 8 Microservices

| # | Microservice | Port | Responsibility |
|---|---|---|---|
| 1 | **Prosumer** | 8080 (Group A) | CRUD for prosumers; stores in MySQL via JDBC |
| 2 | **UtilityOperator** | 8081 (Group A) | CRUD for utility operators and grid zones |
| 3 | **Telemetry** | 8082 (Group A) | Consumes Kafka topics (AssetID-ZoneID format); stores time-series data |
| 4 | **AssetLink** | 8080 (Group B) | Associates prosumers ↔ utility operators; publishes to Kafka topic per link |
| 5 | **FlexibilityEvent** | 8081 (Group B) | Analyses telemetry; emits flexibility offers to Kafka if SoC > 90% at peak |
| 6 | **EnergyAnalytics** | 8080 (Group C) | Aggregates system-wide energy data by zone/prosumer |
| 7 | **GridBalancing** | 8081 (Group C) | Cross-zone analysis; produces balancing recommendations |
| 8 | **FlexibilityForecasting** | 8080 (Ollama EC2) | Uses Ollama LLM (llama3.2) to analyze past flexibility event logs |

### Technology Stack

| Layer | Technology |
|---|---|
| Microservices | Quarkus 3.27.2 (reactive), Java 21 |
| Database | AWS RDS MySQL |
| Message Broker | Apache Kafka 4.1.1 (KRaft mode, 3-broker cluster) |

## Kafka Architecture

- **3-broker KRaft cluster** (no Zookeeper) using Kafka 4.1.1
- `controller.quorum.voters` format: `1@host1:9093,2@host2:9093,3@host3:9093`
- **Topic naming convention**: `{AssetLinkID}-{UtilityOperatorID}` (e.g., `560987123-EDP`)
- Telemetry microservice dynamically subscribes to topics via `/Telemetry/Consume` REST endpoint
- `DynamicTopicConsumer` uses `auto.offset.reset=earliest`

## Telemetry Message Format

Three asset types, all with common header:

**Common Header:**
```json
{ "timeStamp": "ISO8601", "asset_type": "BATTERY|SOLAR|EV_CHARGER", "asset_id": "string", "grid_cell_id": "string", "payload": {...} }
```

**BATTERY payload:** `soc_percent`, `energy_available_kwh`, `active_power_kw`, `max_discharge_power_kw`, `soh_percent`, `connection_status`

**SOLAR payload:** `generation_kw`, `daily_yield_kwh`, `ac_voltage_v`, `grid_frequency_hz`

**EV_CHARGER payload:** `connector_status`, `charging_power_kw`, `session_energy_kwh`, `ev_soc_percent`

## Deployment Flow

1. `source ./access.sh` — loads AWS credentials + Docker credentials
2. **Terraform** deploys in order: RDS → Kafka → Ollama → Kong → Camunda → Group A → Group B → Group C → FlexibilityForecasting (replaces Ollama EC2)
3. Each group gets `terraform.tfvars` generated with live addresses (RDS, Kafka brokers, upstream services)
4. **Kong routes** configured via `configure_routes.sh` after Kong is ready
5. **BPMN processes** deployed to Camunda REST API at `/v2/deployments` (with `kong-ip` substituted)

Key scripts:
- `DeploymentSprint2.sh` — full automated deployment
- `UndeploymentAutomation-all.sh` — full teardown
- `run_all_tests.sh` — all API tests + telemetry simulation
- `tests/bpmn_test.sh` — end-to-end BPMN process test

## Known Issues & Fixes Applied

| Issue | Root Cause | Fix |
|---|---|---|
| Kafka format error "controller.quorum.voters not set" | Kafka 4.1.1 requires explicit voter list | Changed `controller.quorum.bootstrap.servers` → `controller.quorum.voters` in server.properties |
| ARM64/x86_64 mismatch | WSL builds amd64 images; t4g.small is ARM64 | Changed all group AMIs to `ami-07ff62358b87c7116` + `t3.small` |
| OUTSIDE:// prefix in Kafka bootstrap address | Quarkus DevServices adds `OUTSIDE://` listener prefix | Strip prefix with `replaceFirst("^[^/]+://", "")` in KafkaProvisioningResource |
| Ollama model not available | `ollama pull` as root stores in `/root/.ollama/` | Changed to REST API: `POST /api/pull` (stores under Ollama service user) |
| HCL semicolon syntax error | `variable { type = number; default = 3306 }` invalid | Multi-line format with `{` on its own line |
| Group A/B/C addresses empty | `terraform output -raw` returned empty | Use `terraform state show ... | grep ' public_dns'` |
| Telemetry NULL values | Schema had `NOT NULL` on Status/Plug_Status | Removed `NOT NULL` constraints |
| Kong routes returning 404 | Lowercase paths + `strip_path=true` | Fixed to uppercase paths + `strip_path=false` |
| BPMN user task not completable | Missing `<zeebe:userTask>` extension | Added to all 4 BPMN files with user tasks |
